## Lead 1 (⭐ finds.txt priority): GSQ-RCO IQ2_XS-MTP — REAL, PLAUSIBLE, NOT A CLEAR WIN

Repo: `ISTA-DASLab/Qwen3.8-27B-GSQ-RCO-GGUF` (exists, card verified 2026-09-24).

- **GSQ-RCO is not a custom format.** GSQ = Gumbel-Softmax per-coordinate grid +
  scales; RCO = per-tensor mixed-type allocation under a size budget. Output is a
  **standard GGUF** using mainstream IQ2/IQ3 types → runs on stock/mainline
  llama.cpp, including Vulkan. The "only works on NVIDIA" comment found in search
  is NOT on the model card and contradicts it (card: "run unmodified in llama.cpp,
  Ollama, LM Studio").
- **Files:** IQ2_XS 8.4 GB (2.50 bpw) / IQ2_S 9.3 / IQ3_XXS 10.1 / IQ3_S 11.8;
  `-mtp` variants ≈ +0.35 GB (IQ2_XS-mtp ≈ 8.75 GB). Quality claim (finds.txt,
  card-consistent): LCB v6 76.6 (IQ2_XS) / 82.3 (IQ2_S) vs 85.7 BF16.
- **MTP:** the head (15 tensors, nextn) is embedded in the GGUF — no external
  drafter (finds.txt's "ya no hace falta el drafter externo de 1.37 GB" confirmed).
  llama.cpp PR #22673 added MTP; +33–39% decode reported for Qwen3.8-27B on
  consumer GPUs (CUDA-measured); draft 2–3 recommended; short prompts (~500 tok)
  show muted gains.
- **Vulkan status:** MTP on Vulkan is unproven for RDNA2 specifically, but the
  known bug class is misrouting when Vulkan AND ROCm are both compiled in
  ("MTP with --device Vulkan0 uses ROCm instead of Vulkan", 2026-05) — i.e. it
  *runs* on Vulkan where it's the only GPU backend, which is our house runtime
  (b10964, Vulkan-only). **RUNTIME VERIFIED same day:** both installed runtimes
  (`llama-vulkan-b10964` mainline and `llama-prism-b10685-vulkan` daily driver)
  expose `--spec-type draft-mtp` (plus `--spec-draft-n-max`, default 3, and
  draft-KV flags) → the MTP path needs NO new runtime; only the RDNA2 speedup
  itself is unmeasured.
- **Fit on this rig (the problem):** 8.75 GB > 8 GB VRAM → partial offload of
  ~1–1.5 GB + KV (q4_0 @ 8K ≈ 0.25 GB). RAM has ~7.7 GB free → fits, mmap from Z:.
  Arithmetic: GPU side ~7.3 GB @ ~150 GB/s effective ≈ 49 ms + CPU side ~1.2 GB @
  ~20 GB/s ≈ 60 ms + sync → **~8–9 t/s without MTP; ~11–12 t/s with MTP at good
  acceptance — i.e. at best parity with TQ2_0 (12.2–13 t/s, full GPU, no offload)**.
  Rig history warns partial offload can measure far worse than arithmetic (27B with
  ~7 GB on CPU = 1.2 t/s); 1–1.5 GB offload is an untested, milder regime.

**Verdict:** runnable in principle, quality-attractive (newer base model at 2-bit
that reportedly holds), but speed-wise it competes with, not beats, the daily
driver — and only if (a) our runtime supports MTP and (b) small-fraction offload
behaves. **Next step requires user authorization:** 8.75 GB download to Z: (18.3 GB
free — fits, leaves ~9.5) + a bench/probe day. Decision table:

| Option | Expected | Risk |
|---|---|---|
| IQ2_XS-mtp, offload ~1.5 GB, MTP on | 11–12 t/s if lucky | MTP unproven on Vulkan/RDNA2; offload regime untested |
| IQ2_XS-mtp, MTP off | ~8–9 t/s | worse than TQ2_0 |
| Skip | — | lose nothing today |

## Lead 2: ROCmFPX / Strix tricks — DEAD for gfx1032 (watch item)

Repo: `ciru-ai/ROCmFPX` (README read 2026-09-24).

- Real fork: adds FP2/3/4/6/7-style AMD formats (enum 110–115), **not merged
  upstream** — models quantized with them won't load in stock llama.cpp.
- Validation environment: **Radeon 8060S / gfx1151** (Strix) with TheRock ROCm
  7.15 dev toolchain, NixOS source builds. **No gfx1032/RDNA2 mention anywhere;
  no Windows prebuilts in the README.** finds.txt's "builds Windows y Linux con
  ROCm 7 incluido" is UNVERIFIED (RELEASES.md path 404'd; nothing supports it).
- Backend coverage: FP3 has Vulkan paths; FP2/4/6/7 are HIP/ROCm + CPU only.
  None of it runs our ternary PTQ1_0/TQ2_0 (different formats entirely).
- `pugant/Qwen3.8-27B-MTP-Q4_0_ROCMFP4_STRIX_LEAN` = ROCmFP4 format for Strix
  APUs → needs the fork + ROCm on gfx1151-class hardware. Not this rig.

**Verdict:** closed. gfx1032 gains nothing from ROCmFPX today; the L1/L2 ladder
findings stand. Revisit only if the fork ships gfx1032 targets or upstreams the
FP3 Vulkan kernels for a model we actually want.
